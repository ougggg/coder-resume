ENGINEERING NOTES / 我的工程决策

方案背后，是具体的取舍。

从已有项目与经历中，展开三个实现切片。

01 / 性能

让高频访问
少走一次远路。

企业级智能云图之家

CaffeineRedis
要解决什么

云图库接口的响应效率，需要在频繁访问的数据上得到改善。

我如何实现

组合 Caffeine 本地缓存与 Redis，构建二级缓存体系；使用 Redis SCAN 异步清理策略处理数据一致性。

结果与取舍

项目记录的接口响应速度提升为 400%。本地缓存减少远程访问，也让更新与失效策略成为必须关注的部分。

方案对照 · 只使用 Redis，还是增加本地缓存？+

通用设计分析 · 不作为备选方案的实际测试记录

仅 Redis
缓存集中管理，但命中仍需要一次网络访问。
Caffeine + Redis
本地命中可减少远程访问，同时要处理各实例本地缓存的更新与失效。
选择边界
根据访问热点、数据更新频率和一致性要求判断是否值得增加一级缓存。
02 / 数据边界

共享基础设施，
保留知识的边界。

全栈开发经历 · 多租户 RAG

RedisSearchRAG
要解决什么

多用户使用知识库时，需要各自独立的检索范围。

我如何实现

设计基于 RedisSearch 的逻辑隔离架构，实现单用户独立的知识库检索。

结果与取舍

让检索具备用户边界。逻辑隔离也意味着查询条件与权限校验必须保持一致，不能只依靠前端区分用户。

方案对照 · 共享索引，还是独立索引？+

通用设计分析 · 不作为备选方案的实际测试记录

共享索引 + 逻辑隔离
复用索引和基础设施，需要在服务端落实用户过滤与权限边界。
每租户独立索引
索引边界更直观，但索引数量、管理和维护成本会随租户增加。
选择边界
隔离要求、租户规模和维护成本共同影响方案；这里展示通用对照，不代表项目曾完成两种方案的实测。
03 / 并发

让最后一个名额，
只有一次归属。

智慧便民服务平台

MySQLCAS
要解决什么

预约挂号场景中，并发请求可能同时争抢有限的名额。

我如何实现

采用 MySQL 乐观锁（CAS）机制，将并发控制落实到库存更新环节，防止库存超卖。

结果与取舍

以条件更新判断请求能否成功。高冲突时仍需处理更新失败，并让用户得到明确反馈。

方案对照 · 条件更新，还是先锁定记录？+

通用设计分析 · 不作为备选方案的实际测试记录

乐观锁 / CAS
通过更新条件识别并发冲突，冲突时需要处理失败或重试。
悲观锁
先锁定再更新，竞争时可能出现等待，需要关注事务范围与锁持有时间。
选择边界
由实际冲突程度与业务反馈要求决定；本项目记录采用 MySQL 乐观锁。

实现与指标来自本页项目、经历记录；“取舍”补充对应方案的设计考虑。
